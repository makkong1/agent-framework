# db-diagnose — 측정으로 DB 문제를 능동 진단 (원인분석 → 검증 → 해결)

DB 성능·정합성 문제를 **추측이 아니라 측정으로** 찾아내라. 정적 리뷰(`review`)가 "코드에 문제가 있나 훑기"라면, 이건 **재현·계측으로 실제 문제를 잡아내는** 능동 진단이다.

## ⚠️ 이 문서 사용법 — 표는 체크리스트가 아니다

아래 표·예시는 **점화용(priming)** 이다. **찾을 목록이 아니다.**
- 표에 있는 패턴만 확인하고 끝내면 **실패다.**
- **모든** 대상 메서드에 대해 §1의 4개 축으로 **질문을 스스로 생성**하라. 표에 없는 문제를 못 잡으면 진단이 아니다.
- "이 표에 없으니 문제없음"은 **금지** — 측정 안 했으면 "**미측정**"이라고 적는다.
- 예시 수치·도구는 특정 스택(JPA/Hibernate/MySQL)의 것이다. **다른 스택이면 도구 이름만 갈아끼우고 원리는 그대로** 적용하라.

## 먼저 읽을 문서

- `/CLAUDE.md` (기본 작업 스타일 — 추측 금지, 검증 가능 목표)
- `/docs/ARCHITECTURE.md`, `/docs/ADR.md` (스키마·스택·동시성 결정)

## 철학 (반드시 지킴)

1. 손으로 쓴 SQL 말고 **앱이 실제로 날린 쿼리**를 본다.
2. 하나로 재지 말고 **2개 이상으로 교차검증** — 두 값이 어긋나는 지점이 곧 발견 지점이다.
3. 측정 안 한 건 "문제없음"이 아니라 **"미측정"**이다.
4. "고쳤더니 빨라졌다"는 증거가 아니다 — **인과를 증명**한다(적용→제거→재적용).

## 0. 진단 루프 (모든 DB 문제 공통)

```
① 질문 생성    대상 메서드를 4개 축으로 심문 (§1) — 여기서 앵커링을 깬다
② 재현        실데이터 규모 시드 + 앱 기동 + 실제 호출 (SQL 손으로 X)
③ 계측        축마다 맞는 도구 (§2)
④ 교차검증    도구 2개 이상 — 불일치 = 함정 발견 (§3)
⑤ 원인 특정   실행계획 예상 vs 실제 / 통계 / 락 — 증거로
⑥ 해결 후보   여러 방법 + 트레이드오프, 성능만으로 결정 X (§4)
⑦ 인과 증명   A/B/A, before는 이전 커밋을 실제 실행(추정 X)
⑧ 회귀 방지   테스트가 "결함을 실제로 잡는지" 먼저 확인 (§5)
```

각 단계에서 먼저 물어라: **"내가 지금 뭘 못 보고 있나?"** 이 스킬의 값어치는 ①④에 있다.

---

## 1. 질문 생성 — 4개 축 (핵심: 아무 메서드나 여기에 넣어라)

체크리스트를 외우지 말고, **대상 메서드를 이 4축으로 심문**해서 매번 질문을 새로 만들어라. 어떤 도메인·어떤 쿼리든 이 축은 성립한다.

| 축 | 그 메서드에 던지는 질문 | 놓치기 쉬운 신호 (예시 — 전부 아님) |
|---|---|---|
| **① 왕복 (round-trips)** | 이 호출이 DB에 **몇 번** 가나? 루프·LAZY 로딩·DTO 변환기 안에서 반복되나? | 목록 조회 후 행마다 연관 접근(N+1), 단건 변환기를 목록에 행마다 호출 |
| **② 스캔 (rows examined)** | 각 쿼리가 **몇 행을 훑나**? 인덱스를 타나? 정렬이 인덱스로 끝나나 아니면 filesort인가? | 인덱스가 있는데도 안 쓰임(통계/선택도 오판), 복합 인덱스 선행 컬럼 불일치 |
| **③ 결과·부수 쿼리** | **몇 행/몇 바이트** 돌려주나? 상한·페이징 있나? 이 호출이 **눈에 안 보이는 쿼리를 동반**하나? | 페이징 반환 시 자동 COUNT 동반, 상한 없는 전체 반환, 깊은 OFFSET |
| **④ 락·정합성** | 동시 접근 자원인가? 락을 잡나? 락 **순서가 일관**되나? 원자성이 보장되나? | Lost Update, 정원 초과, 락 승격 데드락, 넓은 트랜잭션의 커넥션 장기 점유 |

> **규칙**: 4축 각각에 대해 "측정했다/미측정"을 명시하라. 한 축이라도 "안 봤다"면 진단은 미완이다.

---

## 2. 축 → 계측 도구 (JPA/MySQL 예시 — 스택 다르면 대응물로 치환)

| 알고 싶은 것 | 1차 도구 | 교차검증 |
|---|---|---|
| 앱이 진짜 날린 쿼리 | 앱 기동 + 실제 호출 + SQL 로그 on(`show-sql`) | — (여기가 기준점) |
| ① 왕복/쿼리 개수 | SQL 로그를 센다(`grep -c`) | ORM 통계 API |
| ① 진짜 DB 왕복 수 | 준비된 statement 카운터 | 실행 쿼리 카운터(LAZY 누락 주의) |
| ② 어떤 쿼리가 비쌌나 | 서버측 쿼리 통계(검사행순·호출횟수순·쓰기) | 실행계획 실측 |
| ② 계획이 왜 나쁜가 | 실행계획 **실측**(예상 rows vs 실제 rows, 반복횟수, filesort/temp) | 계획 JSON |
| ② 인덱스 있는데 왜 안 쓰나 | 옵티마이저 **통계/히스토그램** | 통계 갱신 후 계획 재확인 |
| ④ 락 경합 | 엔진 **행 락** 대기/시간 카운터(전역) | 엔진 상태 덤프 |

> **N+1은 검사행순으로는 안 보인다.** 값싼 쿼리가 수백 번 반복돼 각각은 싸기 때문 — 반드시 **호출횟수순(①)**으로도 봐야 한다.

## 3. 측정 함정 — 원리 (닫힌 목록이 아니다)

**메타 원리 하나만 기억하라:**
> 도구를 믿기 전에 **도구부터 의심**한다. 같은 값을 **2개의 독립 경로**로 재서 **어긋나면**, 그 어긋남이 곧 새 함정(또는 새 버그)의 발견 지점이다.

아래는 **지금까지 관측된 예시**다. 계속 늘어난다 — 여기 없는 함정을 만나면 추가하라.

| 함정 (예시) | 무슨 일이 벌어지나 | 대응 |
|---|---|---|
| **집계가 왕복 수를 줄여 보이게 함** | 조인 페치·배치 페치가 N개 로딩을 IN 쿼리 1개로 접음 → "쿼리 수"만 보면 문제가 사라진 듯 보임 | 쿼리 **개수**와 **검사 행수**를 **따로** 본다. 개수↓라도 스캔량은 그대로일 수 있다 |
| **실행 쿼리 카운터 과소보고** | 명시 쿼리만 세고 지연 로딩을 안 셈 → 최적화를 되돌릴 뻔 | 준비된 statement 카운터 |
| **ORM 통계가 절반만 보고** | 파생·지연 초기화 미집계(예: 실제 41개를 21개로) | 최종 카운트는 **SQL 로그**를 센다 |
| **락 시간 지표가 행 락을 0으로** | 테이블 락만 세고 엔진 행 락을 안 잡음 → "락 대기 없음" 오판 | 엔진 행 락 카운터(전역) |
| **빌드 캐시가 재실행을 스킵** | DB 상태는 빌드 입력이 아니라, 인덱스/통계를 바꿔도 소스 같으면 옛 결과로 통과 | clean 후 재실행/캐시 무시 |
| **손으로 쓴 SQL로 측정** | 앱이 실제 붙이는 부수 쿼리·컬럼(큰 텍스트 등)을 빠뜨려 비용이 달라짐 | 앱 기동 + 실제 호출 |
| **작은 픽스처** | 소규모에선 어떤 계획을 골라도 차이 없음 → 계획·인덱스 문제가 안 나타남 | 실데이터 규모 시드(단 N+1은 규모 무관) |
| **에러를 삼킴(`2>/dev/null`)** | 재현 실패를 못 보고 "재현 안 됨" 오결론 | 에러를 드러내 놓고 측정 |

## 4. 해결 — 후보 + 트레이드오프 (성능만으로 결정하지 않는다)

문제 하나에 답은 여럿이다. **후보를 나열하고 트레이드오프와 함께** 고르라.

- **N+1(다대일)**: 조인 페치 / 엔티티 그래프 — 행이 안 늘어 안전.
- **N+1(컬렉션)**: ID를 `IN`으로 묶어 **배치 조회** 후 `Map` 병합 — 조인 페치는 카티전 곱 뻥튀기.
- **자동 COUNT 비쌈**: `countQuery` 분리 / 총건수 불필요 시 Slice / 조인 컬럼 비정규화.
- **깊은 페이지**: 키셋(커서) vs 지연조인 — 키셋 최고성능이나 페이지번호·"맨 뒤" UI를 못 지원할 수 있음.
- **인덱스 있는데 filesort**: 행수 통계 갱신 → 그래도면 **히스토그램**(코드·인덱스 추가 0, 단 조용히 회귀 → 계획 재검증 필요).
- **카운트/인원 동시성**: 조건부 원자 UPDATE(현재값 검증 불필요 시).
- **잔액 동시성**: 비관적 락("부족" 분기 태우려면 현재값 필요).
- **데드락**: 락 획득 **순서 통일**(같은 트랜잭션이면 순서만 바꿔도 정합성 동일).
- **대량 적재**: 배치 단위 + 트랜잭션 분리(부분실패 격리) + 컨텍스트 clear.

> 스택·도메인에 따라 후보는 달라진다. 위는 **사고의 출발점**이지 정답표가 아니다.

## 5. 검증 — "통과하는 테스트"가 아니라 "결함을 잡는 테스트"

- **before는 재구성이 아니라 실제 이전 코드**: 이전 커밋/워크트리로 띄워 재측정(추정 금지).
- **A/B/A 인과 증명**: 적용→제거(되돌아옴 확인)→재적용. 개선 사실만으론 인과가 안 잡힌다.
- **테스트가 결함을 실제로 잡는지 먼저**: 수정을 되돌린 상태에서 테스트가 **빨간불**인지 확인 → 그 다음 초록불. 이 앞단이 없으면 "통과만 하는" 테스트다.
- **동시성은 단일 호출로 관측 불가** → 격리 DB에서 래치·트랜잭션 우회로 결정론적 재현.
- 측정 못 한 범위는 결과에 **"미측정"**으로 명시.

## 산출물 형식

```
## 원인 분석
- 증상: (무엇이 느린가/틀리나)
- 질문 생성: (§1 4축 중 어디를 심문했나 — 각 축 측정/미측정)
- 계측: (§2 어느 도구)
- 교차검증: (도구 2개 결과 — 어긋났다면 §3 어느 함정)
- 원인 특정: (실행계획 예상 N vs 실제 M / 통계 / 락 — 증거)

## 검증 방법
- 재현: 시드 규모 + 실제 호출 / 동시성이면 래치
- 인과: A/B/A 결과

## 해결 방법
- 후보 + 트레이드오프 (§4), 택한 이유(성능만 아님)
- 회귀 방지: 결함 잡는 테스트(빨간불 먼저 확인)
```

---

## 워크플로우 연계
- 진단 완료 → 수정은 `refactor`(구조·성능) 또는 `fix`(버그) → `test`(회귀) → `commit` → `docs-sync`.
- 정적 훑기가 먼저면 `review`, 능동 재현·계측이면 이 커맨드.

## 제약
- 추측으로 결론 내지 않는다 — 앱이 실제 날린 쿼리와 도구 2개로 확인한 뒤 쓴다.
- 도구를 믿기 전에 도구부터 의심한다(§3). 한 도구 숫자만으로 개선/롤백을 결정하지 않는다.
- 표를 체크리스트로 소비하지 않는다 — 4축으로 질문을 **생성**한다.
- 부풀리지 않는다. 수치엔 측정 조건(주 지표=쿼리 수, 시간 보조, 시드 규모)을 함께 적는다.
